# Repository Guidelines

## Project Structure & Module Organization
`StenUNet/` hosts the deep-learning workflow for stenosis detection, with training logic in `training.py`, data orchestration in `training_planning.py`, and runtime inference in `inference.py`; supporting transforms and post-processing live under `pre_process/` and `post_process/`. `centerline_pipeline/` is a lightweight Python package that turns binary vessel masks plus `annotations.json` into centerlines and per-point metrics; its modules (`distance.py`, `path.py`, `visualization.py`, etc.) are designed to stay importable in isolation. `centerline/` contains the legacy MATLAB scripts and generated outputs (`centerline/output/`) that back the pipeline reference cases, while the active masks and annotations now live under `annotation/labelsTr/` and `annotation/annotations.json`. Both `StenUNet/` and `centerline/` are separate git repositories—run git commands inside those folders; the workspace root itself is not a git repo. Please always use `conda activate centerline` to activate the environment.

## Build, Test, and Development Commands
Create a Python environment, then install the primary dependencies with `python -m pip install -r StenUNet/requirements.txt`. Typical workflows (after `conda activate centerline`):
- Generate centerlines/features: `python -m centerline_pipeline --mask-dir annotation/labelsTr --annotations annotation/annotations.json --out centerline/output --limit 1` then `python centerline/centerline_pipeline/generate_features.py` (feature maps land in `centerline/output/<case>/data` and figures under `.../figures`).
- Train pseudo-color scalar field (HSV/glowing_tube): `python -m StenUNet.pseudo_color.train_scalar_field --data-root centerline/output --output-dir StenUNet/pseudo_color/runs --val-ratio 0.2 --seed 0 --amp --export-preview` (inputs: `feature_normalized_distance.npy`, `feature_radius.npy`; target: `feature_pseudo_color.npy`; previews go to `runs/train_png`).
- Infer pseudo-color: `python -m StenUNet.pseudo_color.infer_scalar_field --data-root centerline/output --checkpoint StenUNet/pseudo_color/runs/best_model.pt --output-dir StenUNet/pseudo_color/runs --save-png` (writes `runs/inferences/<case>/data/predicted_pseudo_color.npy` and PNGs under `runs/inference_png`).
- StenUNet planning/training: `python training_planning.py` then `CUDA_VISIBLE_DEVICES=0 python training.py 0 [--use-pseudo-color-map --pseudo-color-dir StenUNet/pseudo_color/runs/inferences]` from inside `StenUNet/`. Set the same flags for `python inference.py -chk ... -i dataset_test/raw [...]` to append predicted pseudo-color channels at runtime.

## Coding Style & Naming Conventions
Follow PEP 8 with 4-space indentation for Python, keep type hints on public functions, and prefer descriptive lowercase module names (`centerline_pipeline/distance.py`). Preserve the current logging-first structure in CLI scripts and favor pure functions over side effects. MATLAB contributions should mirror the existing camel-cased function files and inline documentation style in `centerline/*.m`. Before opening a PR, run an auto-formatter such as `black` (line length 100) and `isort` on touched Python files; avoid committing notebook checkpoints or large binaries.

## Testing Guidelines
Augment or add `pytest` suites under a new `centerline_pipeline/tests/` package; target the geometry helpers (`distance.compute_distance_and_cost`, `path.shortest_path`) with synthetic masks and compare against known pixel paths. Integration smoke-tests should call `python -m centerline_pipeline ... --limit 1` on a copy of `annotation/labelsTr/` to confirm output JSON and overlay images regenerate cleanly. For StenUNet, validate data loaders and augmentations with lightweight unit tests that assert tensor shapes and modality ordering. Document any randomness controls (e.g., seeds, cuDNN flags) inside the tests you create.

## Commit & Pull Request Guidelines
Each component repository (`StenUNet/` and `centerline/`) tracks its own Git history; adopt Conventional Commit headers (`feat:`, `fix:`, `docs:`) followed by an imperative summary (<50 chars) so changelogs remain scriptable. Reference related issues in the body, list validation commands you ran, and attach before/after artifacts (metrics tables, overlay previews) when they help reviewers. PR descriptions should outline motivation, note data requirements, flag any migrations to `nnUNetPlans.json`, and include clear rollback instructions when altering training checkpoints.

## Data & Security Notes
Keep protected clinical data outside the repo; instead, document expected directory names (`dataset_test/raw`, `nnNet_training/Raw_data/`) and rely on `.gitignore` to block accidental inclusion. Strip PHI from overlays before sharing screenshots, and store model checkpoints in encrypted buckets—only reference their paths in docs. When publishing scripts that touch remote storage, expose credentials through environment variables, never hard-coded constants.
